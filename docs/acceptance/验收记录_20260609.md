## 9. Dify 不可达原因与恢复记录

2026-06-09 恢复前定位结论：

- `.env.dify_rag` 中 `DIFY_BASE_URL=http://127.0.0.1:8081`，Demo 配置指向 Dify nginx 入口。
- `127.0.0.1:8081` 恢复前无监听，请求返回“目标计算机积极拒绝连接”。
- `127.0.0.1:8080` 有服务，但实际是 `sub2api` 容器，不是 Dify，页面标题为 `Sub2API - AI API Gateway`。
- Dify compose 项目位于 `D:/newwork/lab-safe-assistant-workspace/lab-safe-assistant-github/local_env/dify/docker`。
- Dify `nginx` 服务原始端口映射为 `8081:80`，说明 Demo 指向 `8081` 的配置本身合理。
- 恢复前 Dify 容器整体处于停止状态：`docker-api-1 / docker-nginx-1 / docker-web-1 / docker-worker-1` 等为 `Exited (137)`，`docker-db_postgres-1 / docker-redis-1` 为 `Exited (0)`。
- `OOMKilled=false`，不像是容器内部 OOM 崩溃；更像是 Docker Desktop / compose 项目被外部停止后未恢复。

因此，本轮 Dify 不可达的直接原因是：**Dify Docker compose 项目未运行，导致原本映射到 `8081` 的 Dify nginx 入口不存在**。不应把 Demo 改到 `8080`，因为 `8080` 已被 `sub2api` 占用。

恢复动作：

```powershell
cd D:/newwork/lab-safe-assistant-workspace/lab-safe-assistant-github/local_env/dify/docker
docker compose -p docker up -d
```

恢复后复核：

- `docker-nginx-1` 已映射 `0.0.0.0:8081->80/tcp`。
- `http://127.0.0.1:8081` 返回 `200`。
- `scripts/status_dify_rag_local.ps1` 返回 `/health 200`，且 `dify_reachable=true`。
- Dify `/v1/parameters` 使用当前 App Key 返回 `200`。
- Dify `/v1/chat-messages` 使用 `response_mode=streaming` 返回 `workflow_finished / status=succeeded`，输出 `Dify问答链路正常`。
- `scripts/verify_acceptance_route.ps1` 可强制避开缓存，验证普通问题真实进入 `dify-workflow`；本轮多次复核结果包含 `model=dify-workflow`、`decision=dify_answer`，上游耗时约 `5203ms` 到 `24064ms`。

补充观察：曾在 worker 日志中看到 `api-vip.codex-for.me` 的 Cloudflare `521`，发生在自动生成会话标题等模型插件调用场景；本次流式主问答链路已经成功，因此当前验收口径应写为“Dify 平台和主问答链路已恢复，外部模型代理仍需持续观察”。

## 10. Dify 模型线路切换记录

2026-06-09 已将 Dify 中旧的不稳定 OpenAI-compatible 代理线路替换为新的本地可用线路：

- 旧问题：`gpt-5.3-codex` 原模型凭据指向 `api-vip.codex-for.me`，worker 日志中出现 Cloudflare `521`。
- 新配置：保留 Dify 内部模型名 `gpt-5.3-codex`，但将 `llm` 与 `text-generation` 两类模型凭据的 `endpoint_url` 切换为新网关，并将 `endpoint_model_name` 设置为已测通的 `gpt-5.4`。
- 未改动：`deepseek-v4-pro` 凭据保持原配置。
- 缓存处理：清理 Redis 中 provider/model credential 相关缓存，并重启 `plugin_daemon / api / worker / nginx`。
- 复核结果：`scripts/verify_acceptance_route.ps1` 通过，返回 `model=dify-workflow`；自动标题生成触发后 worker 日志显示 workflow 成功，最近复核窗口未再出现旧代理 `521`。

注意：新网关中部分 codex/mini 模型返回“号池没有额度”或超时，因此本轮没有直接使用这些模型作为验收主线路，而是使用实测可返回的 `gpt-5.4` 作为实际转发模型。
