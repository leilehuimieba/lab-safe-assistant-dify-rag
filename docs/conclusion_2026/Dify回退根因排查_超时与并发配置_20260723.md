# Dify `structured_fallback` 根因排查 —— 超时与并发配置分析（2026-07-23）

> 项目：基于 Dify 搭建 RAG 增强的大语言模型实验室安全小助手系统
> 触发：批次D问答质量联动复测（`知识库溯源整改_批次D问答质量联动复测_20260723.md`）在 50 题顺序调用中出现 2 例 `structured_fallback`（EV-003、EV-045），批次D文档已如实记录并把「根治需排查 Dify 容器并发/超时配置」列为待办。本文件完成这一待办的**可确证部分**，并如实标注哪些属于未直接核验的外部环境。

## 1. 结论速览

1. 这 2 次回退是**两种不同的失败模式**，此前被同一句 `upstream unavailable` 掩盖：
   - **EV-003**：客户端读超时——生成耗时约 127 秒，超过 `DIFY_TIMEOUT=120s` 读超时；
   - **EV-045**：**非超时**——约 34 秒后上游返回空/错误（未达 120s 超时线）。
2. `DIFY_TIMEOUT=120s` 对正常问答**并不紧**：同样这两题单独复测的真实上游耗时仅 **10.3s / 11.9s**，有约 10× 余量。回退的诱因是**瞬时资源竞争**（批量顺序请求叠加本机当时并行的其他后台任务），不是超时阈值设错。
3. **本次已修复一个真实的可观测性缺陷**：回退路径此前丢弃了 `call_dify_lab` 抛出的 `HTTPException.detail`，且不给 `upstream_ms` 赋值（停在 0），导致下一次回退仍无法区分失败模式。本次让失败原因可分类、可记录（代码改动见第 4 节）。

## 2. 证据重建（来自留存的原始 eval JSON）

数据源：`artifacts/conclusion_2026/eval_50_20260723_batchD_post_traceability/eval_set_v2_50_raw.json`（批量复测原始返回）与 `.../eval_50_20260723_batchD_recheck_fallback/eval_recheck_raw.json`（两题单独复测）。

| 题号 | 批量复测 server_elapsed | 批量 upstream_ms | 决策 | 单独复测 upstream_ms | 单独复测决策 |
|---|---:|---:|---|---:|---|
| EV-003 | 126981 ms（≈127s） | 0 | structured_fallback | 10264 ms | dify_answer |
| EV-045 | 34116 ms（≈34s） | 0 | structured_fallback | 11929 ms | dify_answer_guarded |

关键读法：

- 批量复测里两条的 `upstream_ms` 都是 `0`——**不是**说上游没被调用，而是旧代码只在 `call_dify_lab` **成功返回后**才给 `upstream_ms` 赋值（`chat_routes.py` 的 try 块内），异常路径直接跳过，字段留在初始 0。真实的「失败耗时」被丢弃，只能从 `server_elapsed_ms` 反推。
- EV-003 的 ≈127s 正好压在 `DIFY_TIMEOUT=120s` 读超时线之上（120s 读超时 + 连接/检索/首字节等开销）→ 判定为**读超时**。
- EV-045 的 ≈34s **远低于** 120s 读超时线，也超过 20s 连接超时不影响（连接是本机 8081，瞬时完成）→ 不是超时，而是 `call_dify_lab` 在约 34s 后因**上游空返回/错误事件**抛出 502（对应 `dify_empty_answer` 或 `dify_http_5xx` 路径）。
- 两题单独复测均在 10–12s 内走通真实 `dify-workflow`，证明**问题不在这两题本身、也不在 Dify 工作流定义**，而是当次批量运行时的瞬时状态。

## 3. 超时与并发配置分析

### 3.1 客户端侧（本仓库内，可确证）

`web_demo/services/upstream_service.py::call_dify_lab`：

```python
timeout = float(os.getenv("DIFY_TIMEOUT", str(DIFY_DEFAULT_TIMEOUT)))  # 默认 120s
requests.post(endpoint, ..., timeout=(20, timeout), stream=True)       # (连接20s, 读120s)
```

- `DIFY_DEFAULT_TIMEOUT = 120.0`（`web_demo/repositories.py`），`.env.dify_rag` 实配 `DIFY_TIMEOUT=120`。
- 连接超时 20s、读超时 120s。对正常 10–12s 的问答余量充足；EV-003 触线是因为该次生成异常慢（约 12× 正常），而非阈值偏低。
- **判断**：不建议为这 2 例把 `DIFY_TIMEOUT` 无限调高——正常问答根本用不到 120s，一味抬高只会让「真卡死」的请求拖更久才兜底，反而恶化答辩现场体验。若评审要求，可小幅上调到 150–180s 作为对偶发慢生成的缓冲，但这治标不治本，真正的瓶颈在 3.2。

### 3.2 Dify 容器侧（外部部署，未直接登录容器核验）

**诚实边界**：Dify 是本项目之外的标准 docker 部署（`DIFY_BASE_URL=http://127.0.0.1:8081` 指向本机 Dify），其 `docker-compose` 与容器内配置**不在本仓库**，本次排查**没有**登录 Dify 容器读取其真实运行参数，因此以下是「应检查的位置」而非「已核实的数值」，不编造具体配置值：

- `api` / `worker` 服务的并发：Dify 的 `SERVER_WORKER_AMOUNT`（gunicorn worker 数）、`CELERY_WORKER_AMOUNT`。worker 偏少时，多请求叠加会排队。
- `api` 的 gunicorn 超时：`GUNICORN_TIMEOUT_SECONDS`（Dify 默认较大，一般不是本现象主因）。
- 反向代理超时：Dify `nginx` 的 `proxy_read_timeout` / `NGINX_PROXY_READ_TIMEOUT`。
- **最可能的真实瓶颈**：Dify 工作流实际调用的 **LLM 后端**（模型推理服务）在当次被其他进程抢占 CPU/内存 → 单次生成从 10s 劣化到 100s+。批次D复测是**顺序**请求（非压测），本机又同时在跑其他后台任务，这与现象吻合。

**结论**：现有证据不足以断定是 Dify 的 worker 数还是 LLM 后端算力竞争，但两者都指向**瞬时资源竞争**而非确定性配置错误。若要在容器侧根治，应在部署主机上核对上述 Dify 环境变量、并保证 LLM 推理后端在运行期不被其他任务抢占算力。

## 4. 本次代码层改动（可观测性修复）

问题：回退发生时，`chat_routes.py` 的 `except HTTPException:` 既没接住 `exc.detail`，也没记录失败耗时，所有回退都退化成一句无差别的 `upstream unavailable`——正是本次排查不得不靠 `server_elapsed_ms` 反推的原因。

改动（`web_demo/routers/chat_routes.py`）：

1. 新增 `_classify_dify_failure(detail)`：把 `call_dify_lab` 的 `HTTPException.detail` 归类成稳定的中文短标签（`上游响应超时` / `上游未返回有效内容` / `上游返回错误` / `上游连接失败` / `上游配置错误` / `上游暂时不可用`），**只返回短标签、不回传上游原始报文给用户**。
2. `except HTTPException as exc:` 分支：
   - 补记 `timings["upstream_ms"]` = 失败耗时（不再停在误导性的 0）；
   - `logger.warning(...)` 把**原始 detail + 失败耗时**写入服务端日志，供深度排查；
   - 兜底答案的「备注」由 `low_reason or fallback_reason` 决定——KB 本身低置信时仍优先显示 KB 原因，否则显示分类后的上游失败原因，取代原来无差别的 "upstream unavailable"。
3. 新增回归测试 `tests/test_dify_fallback_reason.py`（7 用例），锁定各失败模式的分类映射，并断言标签不会回传上游原始报文。

行为影响：正常成功路径完全不变；仅在**已经发生回退**时，让「为什么回退」变得可读、可分类、可在日志中定位。全套测试 **58 passed（+6 subtests）**，`quality_gate.py` 通过。

## 5. 建议

1. **答辩现场**：避免连续快速重复提问；若单题偶发走到兜底模板，直接重新提问即可（已多次验证能走通真实 `dify-workflow`）。
2. **运行期**：7x24 监测/评测运行时，尽量不与其他重负载任务共用同一台机器抢占 LLM 后端算力（云主机常开环境已是更稳的方向）。
3. **可选调参**：若评审要求对偶发慢生成留缓冲，可把 `DIFY_TIMEOUT` 从 120 小幅上调到 150–180s；同时在 Dify 部署主机上核对 `SERVER_WORKER_AMOUNT` 等并发参数。二者均为缓解措施，非确定性修复。
4. **持续观察**：本次可观测性修复上线后，后续若再现回退，可直接从服务端日志的分类标签与 `upstream_ms` 判定失败模式，无需再反推。

## 6. 诚实边界说明

- 本文件所有耗时/决策数字均来自留存的 eval 原始 JSON，未编造。
- 「两种失败模式」的判定基于 `server_elapsed_ms` 与超时阈值的对比，是**基于现有证据的合理推断**；EV-045 的确切上游返回内容（空 vs 5xx）在旧代码下未被记录，本次修复后方可在未来精确捕获。
- Dify 容器内的真实并发/超时数值**未经本次直接登录核验**，第 3.2 节只列出「应检查的配置项」，不给出未证实的具体取值。
- 本次代码改动是**可观测性增强**，不改变上游调用逻辑，也不能凭空消除瞬时资源竞争这一外部诱因；它让下一次回退可被快速归因，而非保证不再发生。
