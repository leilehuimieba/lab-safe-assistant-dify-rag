# 历史真实运行证据补充（2026-07-23）

## 说明

本文档补充记录 2026-07-23 从服务器系统日志、容器运行时状态中挖掘到的**真实历史证据**，
用于说明本地 7x24 结构化健康检查快照存在监测空白（尤其是 2026-06-16~07-15 共 30
天的连续空白，详见 `7x24每日阶段证据总览_20260723.md`）期间，服务本身的真实运行情况。

**重要边界声明（请在引用本文档时保持这一区分）**：

- 以下证据均为**已经存在、真实产生的系统日志/运行时状态**，采集时间为
  2026-07-23，但记录的是过去数月内系统自身留下的时间戳，不是伪造或倒填的数据。
- 以下证据**不是**结构化健康检查快照——它们不包含响应时间、KB 加载条数、
  置信度等定量健康检查指标，只能证明"进程/容器在某段时间内持续运行、未重启"，
  不能替代 `health_snapshots.csv` 中逐次采集的健康检查记录。
- 本文档**不会**、也不应被用来往 `health_snapshots.csv`/`.jsonl` 里补写过去日期的行。
  如需查看正式的逐日快照证据，仍以 `daily_index.csv` 与
  `7x24每日阶段证据总览_20260723.md` 为准。

## 2. 远程服务器：web_demo 应用进程持续运行约 56 天

排查 `labsafe.service` 崩溃重启循环（详见 [[远程主监测环境接入记录_20260723]]）
时发现，真正对外提供服务的是一个不受 systemd 管理的孤立进程（早于本次接入前就已启动）：

```
PID    PPID     ELAPSED       CMD
1760102 1760101 56-20:43:43  .venv/bin/python -m uvicorn web_demo.app:app --host 0.0.0.0 --port 8088
```

`ELAPSED` 为该进程自身的存活时长，56 天 20 小时 43 分钟（查询时刻约
2026-07-23 14:0x），据此反推该进程约自 **2026-05-27** 前后开始持续运行，
与该服务器上代码最后修改时间（2026-05-27 17:39）一致。这意味着：即便
systemd 层面因端口冲突反复崩溃重试（详见下节），真正处理用户请求的服务
实际从未真正中断。

## 3. 远程服务器：systemd 崩溃重启计数的真实性质

`journalctl -u labsafe.service` 显示（受日志轮转限制，只能追溯到约 2026-07-07）：
2026-07-07 07:35 时重启计数已为 409171 次，到 2026-07-23 14:30 增长到 573082 次，
16 天内增加约 16.4 万次，平均每 8~9 秒一次。逐条日志显示固定模式：

```
Started labsafe.service → Application startup complete
→ ERROR: [Errno 98] address already in use → shutdown → 退出 → 5秒后重试
```

即每次重启都在应用启动完成后，因端口已被第 2 节所述孤立进程占用而立即失败退出。
**这是 systemd 监督层面的持续重试噪音，不代表服务真实中断** —— 结合第 1、2
节的证据，实际对外服务从 2026-05-27 起到本次修复（2026-07-23）期间没有真正断线。

修复后（2026-07-23 起）该重启循环已解除，`labsafe.service` 现由 systemd 正常管理运行。

## 4. 未采纳的证据来源（如实说明）

- **本地 Windows 任务计划程序历史**：`Microsoft-Windows-TaskScheduler/Operational`
  事件日志在本机默认未启用（`IsEnabled: False`），因此无法找回
  `LabSafeAssistant-DailyRuntimeCheck` 任务过去的逐次真实执行时间戳，只能看到最近一次
  （`LastRunTime: 2026-07-23 14:03:32`）。这是本机环境限制，如实记录为"该数据源不可用"，
  不做推测或估算式填补。
- **远程 nginx access log**：核查后确认该日志只覆盖默认站点（端口 80，公网扫描器噪音，
  如 `/wp-admin/install.php` 等常见扫描路径）与 Obsidian WebDAV 站点（端口 8090），
  labsafe 应用（端口 8088）并未经过 nginx 反代，因此该日志与本项目服务可用性无关，未采纳。

- 本地工作站采集的 `health_snapshots.csv` 中 2026-06-16~07-15 的空白，**仍应如实计为
  监测记录空白**，不应改写或删除；但结项材料在描述"服务实际可用性"时，可以引用本文档
  第 1、2 节的证据，说明"记录空白"不等同于"服务真实下线"——期间存在一套独立部署、
  持续在线的远程环境提供实际服务能力。

  > 2026-06-16 至 07-15 期间，本地工作站监测记录存在空白（详见每日证据总览），
  > 但同期一台独立部署于云服务器的实例（Docker 容器与应用进程运行时长证据显示）
