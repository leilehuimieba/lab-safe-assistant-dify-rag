## 1. 制定这份计划书的目的

这份计划书不是为了再写一轮材料，而是为后续执行提供唯一主线，避免项目继续出现下面三类跑偏：

1. **只修零散功能，不对齐申报书指标；**
2. **只补文档口径，不补真实能力闭环；**
3. **同时开太多支线，导致准确率、性能、长期运行三条主问题都收不住。**

因此，从本文件落地开始，后续推进统一遵循：

> **先对齐申报书目标 → 再用量化回归约束改动 → 最后补文档和证据。**

## 2. 申报书对项目提出的硬要求

根据原申报书抽取结果，后续工作统一围绕以下 8 项硬要求推进：

### 2.1 核心建设目标

1. 构建 **≥3000 条结构化知识库**
2. 完成 **LLM + RAG** 问答链路
3. 提供 **符合用户习惯的交互界面**
4. 建立 **量化评估体系持续优化**

### 2.2 重点突破目标

1. **精准检索生成**
2. **知识动态更新**
3. **多轮对话理解**
4. **安全可靠性**（低置信度、人工干预、高风险过滤）

### 2.3 最终高目标

1. 有效回答率 `>95%`
2. 专业准确率 `>99%`
3. 响应时间 `<3s`
4. 支持 `7×24` 服务
5. 完成 `3` 个月试运行

## 4. 后续执行总原则

## 4.1 优先级原则

后续只按下列优先级推进，不再随意扩 scope：

### P0：先把“评测与验收尺子”立住

没有尺子，任何“优化”都是主观感觉。

### P1：再把“影响申报书核心指标的功能”补强

重点是：

1. 精准检索
2. 多轮理解
3. 动态更新
4. 安全可靠性

### P2：再做性能与长期运行

因为 `<3s`、`7×24`、`3个月试运行` 都需要稳定证据链。

### P3：最后统一更新对外材料

所有文档口径必须由真实数据和回归结果反推，不反过来“写目标代替达成”。

## 4.2 不做什么

为避免偏航，本阶段明确不优先做以下重扩展：

1. 不先上重型 IoT / 环境监控平台
2. 不先做复杂联邦学习 / LoRA 协同框架
3. 不先把系统扩成多业务平台
4. 不先围绕答辩截图做大量装饰性工作

这些内容可保留为“申报书扩展愿景”，但不作为当前主验收闭环。

## 第二阶段：建设“量化评测闭环”（优先级最高）

### 目标

把“感觉系统差不多”升级为“能按类别量化判断是否变好”。

### 要做的事

1. 统一当前评测资产：
   - `eval_set_v1.csv`
   - 20 题正式评测
   - 50 题人工评分
2. 形成 v2 回归分桶：
   - 危化品
   - PPE
   - 标签 / 储存 / 危废
   - 设备
   - 应急
   - 高风险拒答
   - 多轮追问
   - 模糊问题 / 需补充信息
3. 明确每题期望：
   - `expected_action`
   - `expected_lane`
   - `should_refuse`
   - `should_use_fast_path`
   - `should_request_more_info`
4. 建立评测输出格式：
   - 总通过率
   - 分类通过率
   - 主链路平均耗时
   - 快答命中率
   - 高风险拦截正确率

### 阶段退出条件

至少能稳定回答：

1. 当前哪些类别最弱？
2. 哪些题应该走快答但没走？
3. 哪些题应该拒答但误答了？
4. 多轮题哪里丢上下文？

## 第三阶段：按申报书重点补功能

本阶段只围绕四个申报书重点突破项执行。

### 3.1 精准检索生成

#### 要做的事

1. 优化本地快答命中策略
2. 优化检索召回排序
3. 减少回答泛化和空泛总结
4. 优先引用更贴切的结构化依据

#### 目标

让“专业题答偏”显著减少。

### 3.2 知识动态更新

#### 要做的事

1. 固化知识增量导入流程
2. 明确版本产物与变更日志
3. 形成：
   - 原始资料
   - 清洗结果
   - 导入包
   - 导入报告
   - 生效确认

#### 目标

把“会更新数据”升级为“有可复现更新机制”。

### 3.3 多轮对话理解

#### 要做的事

1. 继续优化 `session_id + conversation_id` 的上下文利用
2. 针对指代、省略、追问补充做专项测试
3. 当上下文不足时，明确触发“请补充信息”

#### 目标

把“支持多轮”升级为“多轮稳定”。

### 3.4 安全可靠性

#### 要做的事

1. 明确低置信度提示场景
2. 强化高风险题的拒答 / 应急分流
3. 明确本地快答只覆盖低风险范围
4. 对模糊高风险问法优先澄清，而不是贸然回答

#### 目标

保证系统在“看起来答得很快”时，依然不越安全边界。

---

## 第四阶段：性能与运行补证

### 目标

围绕 `<3s`、`7×24`、`3个月试运行` 三项高目标积累真实证据。

### 要做的事

1. 把低风险常见题尽量前置到：
   - 本地快答
   - 安全缓存
2. 降低 Dify 主链路上下文和提示负担
3. 建立每日健康检查与每周性能回归
4. 开始记录：
   - uptime
   - 错误率
   - 平均耗时
   - 缓存命中率
   - 快答命中率

### 阶段退出条件

至少形成可持续记录机制，即使 3 个月还未跑满，也要先把证据链开始积累。
